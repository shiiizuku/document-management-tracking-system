# Repository audit — 2026-10-09

Baseline: `main` at `dadc2ae3e9ffdcac0f7461f60006b701b028d3ff`, with a clean working tree before this report. This is a risk-based review of the current codebase and its documented requirements, not a diff review or a penetration test. Findings below are observations from source and tests; concurrency scenarios are reasoned from the code and have not been reproduced against a running database. The `Improvement` column is the proposed next step, not a claim that a fix has landed.

## Standards and implementation integrity

| Priority | Finding and evidence | Improvement |
| --- | --- | --- |
| P1 | **A manual scan verdict can make unscanned bytes downloadable.** The authenticated [`POST .../scan`](../../apps/api/src/modules/files/files.controller.ts) accepts a caller-supplied `CLEAN` result through `recordScan` (`files.controller.ts:132-145`, `attachments.service.ts:273-286`). Administrators and records staff hold `FILE_SCAN_RECORD` (`role-capabilities.ts:45,70`), and download gates on the stored verdict alone (`attachments.service.ts:248-253`). The manual override is intentional (`../IMPLEMENTATION_STATUS.md:348-349`), but policy P-07 says a pending file stays unavailable until the operator requeues scanning (`../policy-register.md:36`). | Replace arbitrary verdict submission with an authenticated rescan/requeue operation that obtains the result from ClamAV. If an emergency override is required, decide and document its approval and evidence requirements separately, then enforce them in code. |
| P1 | **Competing scan writers can replace a final verdict.** `recordScanStatus` reads `PENDING`, then updates by version ID without a `PENDING` predicate (`file-versions.repository.ts:134-158`). Two writers can both pass the read check; the later update can replace the earlier `INFECTED` result with `CLEAN`, contrary to the method's immutable-final-result contract. The existing integration test checks only sequential writes (`files.int.test.ts:187-194`). | Make the transition a conditional `UPDATE ... WHERE scan_status = 'PENDING'`; on zero affected rows, reread and return the same final result or a conflict. Add a concurrent-result integration test. |
| P1 | **Upload steps are not atomic and can race with document closure.** Upload commits a file version, writes its object, changes the document's current pointer, writes audit evidence, then enqueues the scan in separate operations (`attachments.service.ts:133-190`). A failure can leave metadata or bytes without a complete audit or scan intent. Editability is checked before storage I/O (`:106`), while the later pointer update checks only `deleted_at` (`documents.repository.ts:1068-1077`); a release or archive in between can be followed by a new current attachment. This conflicts with the atomic state/event intent requirement (`../Document-management-tracking-system.md:277`). | Recheck editable state and expected document version in the final update; commit pointer, audit, and outbox changes in one database transaction after object storage succeeds. Define retry/cleanup for orphaned metadata or bytes, and test failure and concurrent closure. |

These are code and policy findings, not automated-tool violations. The manual override is documented behavior; the risk is that it weakens the agreed scanner gate.

## Spec coverage

`CONTEXT.md` is the current decision register and takes precedence where older planning text differs (`../traceability-matrix.md:17-21`). The following gaps remain in the current implementation.

| Priority | Requirement and observed gap | Improvement |
| --- | --- | --- |
| P1 | **Missed realtime updates are not reconciled on reconnect.** Decision 128 requires fetching missed notifications from the database (`../CONTEXT.md:254`), and offline catch-up is an MVP acceptance condition (`../Document-management-tracking-system.md:123`). The socket `connect` handler only sets connection state; query invalidation occurs only on a later notification event (`../../apps/web/src/features/realtime/use-realtime-sync.ts:51-58`). | On reconnect, invalidate the inbox/unread and affected document queries or call a cursor catch-up endpoint. Test a notification created while the socket is disconnected. |
| P2 | **The registry and My work use offset and numbered pages.** Amended decision 22 calls for keyset/cursor pages and continuous scrolling because rows change state during use (`../CONTEXT.md:142`). Repository SQL still uses `offset` (`documents.repository.ts:408-413,473-479`), and the registry renders numbered pages (`registry-screen.tsx:168-169,203-210`). | Introduce stable cursor ordering with an ID tie-breaker in the API, then use continuous lists in both screens. Test inserts and status changes between page requests. |
| P2 | **List rows can label pending custody as “In process.”** Pending is derived from an unaccepted route (`../CONTEXT.md:69`). List serialization returns the stored status (`documents.service.ts:293`), which the registry and My work badge (`registry-screen.tsx:110-114`, `my-work-screen.tsx:110-113`); the detail view already presents Pending. | Return a consistent presented status for list rows and test the badge before and after custody acceptance, including for-information copies. |
| P2 | **Dashboard pending work is not actionable in place.** Decision 14 requires authorized accept and section assignment from the dashboard (`../CONTEXT.md:134`). The dashboard provides links to filtered lists, with no action controls (`dashboard-screen.tsx:90-97,208-229,260-279`). | Show a small authorized pending queue and reuse the existing allowed-action flow for accept/assign. Test capability gating and stale-version failures. |
| P2 | **The registry UI omits the section filter.** Decision 20 names section filtering (`../CONTEXT.md:140`). The API accepts `sectionId` (`documents.controller.ts:64-76`), but the registry constructs only the division select (`registry-screen.tsx:176-194`). | Add a section picker scoped to the selected division and keep it in URL state. Test filter combination and clearing. |
| P3 | **Profile photo support stops at the API.** Decision 6 requires upload and display in identity-bearing UI (`../CONTEXT.md:126`). The shell renders initials (`app-shell.tsx:569-580`), and the traceability matrix records no photo UI or endpoint test (`../traceability-matrix.md:58`). | Add upload and display with an initials fallback, then cover the API and UI path. |

The traceability matrix also records partial dedicated incoming/outgoing views and proof gaps (`../traceability-matrix.md:97-98,164-170`). These are already tracked and were not elevated above the verified findings here.

## Local server deployment improvements

| Priority | Finding and evidence | Improvement |
| --- | --- | --- |
| P0 before a pilot | **Production seeding still creates two development users with known passwords.** `seed.ts:75-87,117-130` inserts records and staff accounts with hard-coded passwords regardless of `NODE_ENV`; the production checks cover the administrator and Director but do not prevent these inserts. The production README instructs operators to deactivate or change them after seeding (`README.md:204-208`). | Make production seed create only explicitly configured bootstrap identities, or require unique deployment-provided credentials for every seeded account. Keep demo accounts behind a development-only path. Test the production seed and review any already seeded server for these users. |
| P1 | **Internal services are published on every host interface by default.** Compose publishes PostgreSQL, Redis, MinIO and its console, and ClamAV (`docker-compose.yml:33,49,71,85`), as well as API and web (`:156,214`). The README relies on an operator to firewall or remove ports (`README.md:210-212`); the same topology is used for pilot/production (`../adr/0004-deployment-model.md:17-31`). | Supply a production Compose override or profile that leaves internal services unpublished and binds API/web only to the local reverse proxy interface. Check the rendered configuration and verify external reachability from another host before pilot access. |
| P2 | **Long-running services have no restart policy or documented boot orchestration.** `docker-compose.yml` sets `restart: 'no'` only for the one-shot migrator (`:119`); it specifies none for the seven long-running services. The single-host design depends on restore-from-backup rather than automatic failover (`../adr/0004-deployment-model.md:40-45`). | Set a deliberate restart policy for service containers and document/test how the stack starts after a host or Docker daemon reboot, while keeping `migrate` one-shot. |
| P2 | **Backup freshness is checked manually, with no alert when scheduled copies stop.** The Windows NAS push logs a missing marker or Robocopy result (`../../scripts/push-archive.ps1:20-34`); the runbook asks an operator to watch the first runs (`../runbooks/nas-backup-target.md:112-118`). P-13 requires an off-host recovery point no older than five minutes (`../policy-register.md:42`). A missed scheduled push or object mirror can silently exceed it. | Record last successful WAL push, object mirror, and base backup; alert on stale timestamps or task failures. Verify the NAS copy rather than only the local archive, and include a periodic restore check. |

The production guide already requires TLS, unique secrets, an off-host backup destination, and a reverse proxy. The improvements above make those deployment boundaries explicit and verifiable in the configuration.
