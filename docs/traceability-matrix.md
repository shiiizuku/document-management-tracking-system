# Traceability matrix

_Written 2026-10-07 (box E2, Slice 0.1), against `main` at `8b28b8e`. Rows 4 and 5 updated the
same day, when R-22 closed._

Each source user story is traced to the decisions that govern it, a scope verdict, the code that
implements it, and the tests that prove it. Where a story has no test, the matrix names the
deferral and its reason, or lists the story as a gap.

## How it was built

**The story list is decisions 1–75.** The brief's 75 user stories are not in the repository, its
history or its issues. [`CONTEXT.md`](CONTEXT.md) says decisions 1–75 "retain the attached
functional intent", one decision per story. On 2026-10-07 the project lead agreed to use them as
the story list. Row _n_ is story _n_, worded as decision _n_. If the original wording turns up,
swap it into the Story column. The other columns don't change.

**Decision numbers are `CONTEXT.md`'s.** `D-n` here means decision _n_ in
[`CONTEXT.md`'s register](CONTEXT.md#decision-register-1175), amendments included.
[`Document-management-tracking-system.md`](Document-management-tracking-system.md) §1.10 has its
own D-1–D-151 list with **different numbering**. For example, its D-25 is profile photos, but
`CONTEXT.md`'s D-25 is the signature record. That list is not used here. `CONTEXT.md` takes
precedence where they differ (its "Purpose and authority" section).

**Scope** comes from the `CONTEXT.md` MVP boundary, its later-phase list and policy gates, and
[`policy-register.md`](policy-register.md) (every row `AGREED`). `MVP` means the pilot needs it.
`Deferred` means a decision or agreed policy moved it later, with the reason.

**Tests** were found by searching the suites for the behaviour, then reading each test's title and
body. A file is listed only if a test in it exercises the behaviour. Paths are short:

| Prefix       | Directory                 | Kind                                                     |
| ------------ | ------------------------- | -------------------------------------------------------- |
| `api/`       | `apps/api/test/`          | `*.test.ts` unit and HTTP; `*.int.test.ts` real Postgres |
| `web/`       | `apps/web/test/`          | Component and hook tests (Vitest, Testing Library)       |
| `e2e/`       | `apps/e2e/tests/`         | Playwright, transcribing `acceptance-scenarios.md`       |
| `contracts/` | `packages/contracts/test/` | Shared Zod schema tests                                 |

**Status** values:

- **Covered:** the story is built, and at least one test exercises what it asks for.
- **Partial:** built, but part of the story is missing or untested. The Notes column says which
  part.
- **Gap:** an MVP story with no implementation or no test. Every gap is listed at the end.
- **Deferred:** out of MVP scope, or its proof is explicitly deferred, for the reason given.

## Gaps found

Each gap is tracked in [`risk-register.md`](risk-register.md), owned by the project lead.

**Built short of the decision (R-23).** These work but fall short of what the decision says. Each
needs either the code or an amendment to the decision, which is the project lead's call.

- **D-22 (amended 2026-10-02).** Keyset pages and continuous scroll for the registry and my-work
  were never built. Lists still page by `offset`, which the amendment says double-shows rows as
  documents change state.
- **D-11.** Overdue is visible but not actionable. The dashboard tile has no link, and the
  registry can't filter or mark overdue rows.
- **D-14.** Accept and assign happen on the record, not from the dashboard.
- **D-20.** The web filter bar has no section filter, although the API takes one.
- **D-35, D-36.** There is no dedicated incoming view and no division-grouped outgoing view. Each
  is the registry with a filter.

  screen uses it and no test calls it.

  mock.
