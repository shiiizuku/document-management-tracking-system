# ADR-0003: UUID surrogate keys, separate from human-facing reference numbers

- Status: Accepted
- Date: 2026-09-28
- Deciders: Engineering lead, Records section

## Context

Two different kinds of identifier are needed and are routinely conflated:

1. A **surrogate key** the system uses to join rows and address resources in URLs.
2. A **reference number** humans read aloud, write on paper routing slips, and search by
   — which must be unique per division and gap-free enough to satisfy records practice.

Document URLs are shared between divisions, so a guessable key is an enumeration risk
(the Phase 4 test plan has explicit IDOR cases against guessed IDs).

## Decision

**Surrogate keys are UUIDs**, generated by the database via
`uuid('id').primaryKey().defaultRandom()` in
[schema-helpers.ts](../../apps/api/src/database/schema-helpers.ts). Every table composes
`identityColumns()`, so the convention cannot drift per table. The same helper file fixes
`created_at` / `updated_at` (`timestamptz`, `defaultNow`, `$onUpdate`) and the `version`
integer used for optimistic concurrency.

**Reference numbers are a separate business column**, allocated from the
`reference_counters` table `(division_id, scope_key, next_value)` inside the document
creation transaction. Incoming documents keep the sender's external reference instead of
consuming a counter.

## Consequences

- IDs are non-sequential, so a URL leaks no information about volume or ordering and
  cannot be walked. Authorization is still enforced server-side — unguessability is
  defence in depth, not the control.
- IDs can be generated client-side or in a test before insert, which keeps fixtures and
  outbox idempotency keys simple.
- UUIDv4 keys are random, so heavy insert workloads scatter B-tree writes. At the pilot's
  expected volume this is not measurable; if it becomes so, UUIDv7 is a drop-in change to
  one helper.
- A 16-byte key costs more storage and index space than `bigserial`. Accepted.
- Reference allocation is a contended row. It must be taken with `SELECT … FOR UPDATE` (or
  atomic `UPDATE … RETURNING`) *inside* the create transaction — this is what the Phase 2
  concurrency test proves by creating N outgoing documents in parallel and asserting N
  unique references.

## Alternatives considered

- **`bigserial` primary keys.** Rejected: sequential IDs in shared URLs are enumerable,
  and the records office would still need a second, separate reference column anyway.
- **Using the reference number as the primary key.** Rejected: it is division-scoped,
  human-editable in principle, and absent for incoming documents at insert time.
